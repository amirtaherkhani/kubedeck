# v1.2.0 — modular service and tool lifecycle

**Outcome:** databases, monitoring, testing and developer tools can be added one by one as independent, versioned modules. **Depends on:** v1.1.0 operation contract and the existing `ServiceModule`/`InstallationProfile` schemas. The current Helm release registry remains authoritative until a reconciled migration is verified.

| ID | Priority | Work | Observable acceptance |
| --- | --- | --- | --- |
| V12-01 | P1 | Inventory actual Helm ownership and convert **approved** services incrementally to descriptors and installation profiles. Keep module identity separate from machine-specific values and secret references. Describe dependencies as capabilities and distinguish managed tools from external client workloads. | Every adopted descriptor validates against shared Go/TypeScript schema and matches actual release, namespace, chart version, values and PVC identity. |
| V12-02 | P1 | Implement planner/reconciler for dependency graph, CRD/operator ordering, version/compatibility checks, dry-run diff and per-module install/upgrade/rollback/uninstall using Helm lifecycle semantics. Support vendor charts and dedicated values without forcing a common chart shape. | Adding one database does not reinstall unrelated releases; failed upgrades have visible rollback/retry state and do not silently delete PVCs. |
| V12-03 | P1 | Add Tool Manager API/UI for discover, configure, enable, disable, install, update and remove; show ownership, required dependencies, endpoints, health, data/backup policy and status. Explicitly handle shared releases such as current `platform-storage` before splitting them. | User can install a selected example module and later remove it through reviewed data-retention choices; other modules keep working. |
| V12-04 | P2 | Publish module authoring guide, compatibility policy, validation and release workflow for open-source contributors. Add contract checks for manifest/schema drift and secret-free examples. | A clean contributor can author and validate a new module without editing core agent/UI code or machine-specific paths; catalog state maps to live ownership. |

**Release gate:** at least one database and one observability/test tool prove independent lifecycle end to end. Existing services are migrated only after ownership and data continuity checks. No raw secrets appear in module files.
