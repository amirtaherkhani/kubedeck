## Verified after restart

- Docker Desktop and its built-in one-node Kubernetes cluster are running; `docker-desktop` is the active context. The `desktop-control-plane` node is Ready on Kubernetes v1.36.1.
- A controlled `docker desktop restart` completed. No PVC/PV deletion was performed. All 15 PVCs remained Bound; all 30 Pods eventually reached Running/Ready. Several workloads had transient readiness/backoff errors during recovery before stabilizing.
- The node reports 10 CPU and about 28.7 GiB allocatable memory. Host free disk was about 336 GiB. The 15 PVC requests total about 84 GiB; actual per-volume used space and a workload budget have not been measured.

The Host Agent LaunchAgent has `RunAtLoad` and a 30-second interval and reports the current address. This is periodic reconciliation, not a persistent daemon. IP-change behavior has not been exercised.
- All 24 historic `.local.dev` service names resolve from this Mac to the current address. Following the retirement of unneeded object storage, the active Ingress inventory has four distinct hosts: `kubedeck`, `infisical`, `nats-monitor`, and `rabbitmq-ui`.
- Normal certificate verification now succeeds after restart: `kubedeck.local.dev`, `infisical.local.dev`, and `rabbitmq-ui.local.dev` returned HTTPS 200. Before retirement, the S3 root returned 403 without credentials, as expected for the unauthenticated S3 API endpoint.
- Core service checks passed: PostgreSQL accepted connections, Redis returned `PONG`, RabbitMQ diagnostics ping succeeded, and NATS direct health endpoints responded through a temporary port-forward.
- Two KubeDeck and 19 platform-storage InfisicalSecret resources reported Ready. The live KubeDeck and Agent Helm charts are still 0.1.1 / app 0.1.0 while repository targets are 0.2.0.

## Resolved after the initial audit

- `https://nats-monitor.local.dev/` now returns HTTP 401 with `WWW-Authenticate: Basic`, confirming Traefik routes to the protected NATS monitoring service at `platform-storage/nats-monitoring:8222`. The NATS broker/client endpoint remains `platform-storage/nats:4222`.
- Diagnosis found two configuration issues: Docker Desktop lacked several Traefik v3 provider CRDs, and the Infisical-managed Basic Auth Secret contained both its source field and rendered `users` field. Traefik's log confirmed the two-key Secret prevented middleware construction. PR #28 installed the complete Traefik 3.6.12 provider CRD set; PR #29 corrected the Secret template and upgraded `platform-storage` to 0.1.9. Live Secret key names were verified as exactly `users`; credential values were not read or exposed.

## Infisical recovery progress — 2026-10-07

The earlier failed/incomplete findings above describe the original audit. A new protected backup now exists at `/Users/mac/Documents/Protected Backups/KubeDeck/Infisical/infisical-2026-10-07.sparsebundle` on this Mac. It is an AES-256 encrypted APFS image under a private parent directory. Its passphrase is held in the macOS Keychain item `dev.kubedeck.infisical-backup.2026-10-07`; do not put it in Git, logs, or a release artifact. The image contains a PostgreSQL 16.4 custom-format database dump, PostgreSQL globals, deployment metadata, original Infisical Kubernetes Secret resources (including the encryption key), a manifest, and SHA-256 checksums. The original encryption key in the backup matched the live Secret without disclosing either value.

The archive restored with `pg_restore --exit-on-error` into an isolated PostgreSQL 16.4 pod using ephemeral storage and no Service or TCP listener. All 192 public tables were present. Selected live/restored metadata counts matched: 2 projects, 2 environments, 66 secret folders, and 398 version-two secret rows. The encrypted image was ejected, reopened using the Keychain passphrase, checked against every recorded SHA-256 digest, and ejected again. The restore pod was removed.

This proves backup readability and database restore, **not** complete Infisical recovery. A private decryption/use check against the restored copy is still needed, as is a recoverable off-Mac copy and a restore/reseed decision for the other retained PVCs. The image is local to the current Mac; loss of this Mac could lose both image and Keychain item. Preserve the backup and its key together through a documented recovery process while keeping them separately protected.
