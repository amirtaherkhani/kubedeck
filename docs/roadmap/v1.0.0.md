## DNS and changing LAN IP

The Host Agent's **minimal V1 capability** discovers the active macOS LAN interface/IP, watches network changes, and reconciles Technitium records and Traefik/host listener configuration idempotently. It must not put a chosen Mac IP, network interface, or local file path into shared chart values. Record source address, desired records, last reconciliation, error, and retry/backoff. A short-lived cached record, health check, and restart reconciliation limit stale answers.

Changing service A/AAAA records does **not** update the DNS server address that LAN clients obtained via DHCP. V1-04 must choose and verify one of these bootstrap paths for the actual router: (a) stable DHCP reservation/resolver endpoint for the Mac plus automatic record updates, or (b) supported router/DHCP API integration that advertises the new resolver address to clients and refreshes leases. A stable router DNS resolver with supported conditional forwarding is another valid profile. If none is available, Mac-only DNS can be delivered, but LAN-client access cannot be marked verified. IPv4/IPv6, Wi-Fi/Ethernet transitions, VPN/Private DNS, port 53 conflicts, and router lease renewal must be checked. No WAN exposure is part of V1.

## V1 release gate

- Required service matrix has no untriaged `unknown` or `failed` critical row.
- DNS resolution, TLS, authentication, application response, and persistence pass from the actual Mac and dependent client paths; at least one LAN client exercises the selected DNS bootstrap path and IP-change scenario.
- Infisical development secrets are usable after verified restore, with no values in public evidence. Stateful data survives intended restart or has an accepted reseed policy.
- KubeDeck reports live target state, and each required external project passes its own development smoke flow.
- Rollback assets stay available through the accepted window. Cleanup of old Rancher/DNS resources is a separately recorded action, not a hidden release prerequisite.

**Explicitly out of scope:** separate KubeDeck-owned kind cluster, remote multi-host enrollment, generalized module install/uninstall UI, complete Docker build history UI, Tekton/Buildkite adoption, and WAN access.
