# v1.3.0 — operational data and build visibility

**Outcome:** developers can inspect and operate logs, volumes, containers and builds from KubeDeck without confusing Docker host state with Kubernetes state. **Depends on:** v1.1.0 agents and v1.2.0 module identity.

| ID | Priority | Work | Observable acceptance |
| --- | --- | --- | --- |
| V13-01 | P1 | Collect Kubernetes pod/container logs and events, Docker container logs, structured stream cursor/timestamp/source metadata, retention limits, search/filter and redaction. Provide REST snapshot plus SSE tail. | Logs from both sources identify workload/container, survive reconnect without unbounded replay, and do not expose secrets in saved history. |
| V13-02 | P1 | Model Docker volumes separately from Kubernetes PV/PVC/StorageClass and module-owned data. Expose size/usage where measurable, mounts, owner, backup status, retention and safe detach/delete workflows. | UI identifies a database PVC and Docker volume correctly; any destructive operation checks owner and retention policy. |
| V13-03 | P1 | Track Docker Engine containers/images and BuildKit/buildx active builds plus completed build history, digests, tags, versions, cache and failure diagnostics. Store KubeDeck-initiated build IDs durably; do not imply buildx history covers every still-running build. | Active progress, completed result, provenance and container metadata are queryable after page refresh; failures identify the source and build ID. |
| V13-04 | P2 | Correlate module/service, Helm release, Kubernetes workload, Docker image/build, log stream and observability links. Provide filters, pagination, time bounds and resource-use guardrails. | A service view traces its deployed image to available build metadata and opens relevant logs/metrics without costly cluster-wide polling. |

**Release gate:** representative app, database and build flows work with bounded storage, reconnection and source attribution. Missing metadata is shown as unknown, not fabricated.
