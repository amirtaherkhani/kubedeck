# v2.0.0 — integrated development platform

**Outcome:** KubeDeck coordinates repeatable build, deploy, test, monitor and recovery workflows on top of its stable tools and agents in the current Docker Desktop environment. **Depends on:** v1.2.0–v1.4.0 contracts.

| ID | Priority | Work | Observable acceptance |
| --- | --- | --- | --- |
| V2-01 | P1 | Define application project profiles and reproducible pipelines from source/build image to Helm deployment, development tests and rollback. Integrate existing module dependencies and Infisical references without copying secret values. | A sample external application builds, deploys, runs tests and rolls back using recorded versions and environment references. |
| V2-02 | P1 | Evaluate Tekton (in-cluster task pipelines), Buildkite (external/hosted orchestration with agents) and a small native workflow coordinator against local/offline use, maintenance, resources, security and API integration. Adopt a tool only if it solves a demonstrated pipeline need; neither is the host network manager. | Decision record includes measured pilot, operational cost and chosen integration boundary; unused candidates stay optional modules. |
| V2-03 | P1 | Connect build/deploy/test history to logs, traces, metrics, alerts and service health. Define retention, SLO-style checks, resource limits and recovery drill. | Failed pipeline or degraded service is traceable to exact build/release and actionable diagnostics; recovery exercise succeeds. |
| V2-04 | P2 | Define local cluster resource limits, recovery procedures, and safe boundaries for host and Kubernetes operations. | The current Docker Desktop system has measured capacity limits, a tested recovery procedure, and documented access boundaries. |

**Release gate:** a demonstrated end-to-end developer workflow and documented architecture decisions for the current Docker Desktop environment.
